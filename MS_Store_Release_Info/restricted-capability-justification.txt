================================================================================
Restricted capability justification - runFullTrust
Paste into: Partner Center > Submission options > Restricted capabilities
================================================================================
This is asked on every submission that declares a restricted capability, and it
is asked again on later submissions even when nothing has changed. Keep this
file and paste the same text.

Do NOT remove runFullTrust from the manifest to make the prompt go away. The
package uses EntryPoint="Windows.FullTrustApplication"; without the capability
the application cannot start.


--- SHORT FORM (use this; the box is length-limited) ---------------------------

NanoTorrent is a native Win32 desktop app packaged with the Desktop Bridge and
cannot run in the UWP sandbox.

Shorter still, if needed:

Native Win32 app; cannot run in the UWP sandbox.


--- JUSTIFICATION TEXT ---------------------------------------------------------

NanoTorrent is a native Win32 desktop application, written in Rust and compiled
to a standard Windows executable. It is packaged as an MSIX using the Desktop
Bridge, with EntryPoint="Windows.FullTrustApplication". The runFullTrust
capability is therefore mandatory: this is not a UWP application and cannot run
inside the UWP app container.

The capability is required for the following specific reasons.

1. Win32 executable. The package contains an ordinary desktop .exe rather than a
UWP application. There is no version of this application that runs in the app
container.

2. BitTorrent networking. The application listens on TCP and UDP sockets on a
user-configurable port and makes outbound connections to arbitrary peer IP
addresses discovered through trackers and the distributed hash table. This
peer-to-peer socket use is not expressible with the app container's network
capabilities.

3. File system access to user-chosen locations. Users select arbitrary download
folders anywhere on their drives, including secondary drives and network paths.
Downloaded data must be written, verified against the torrent's piece hashes and
reopened across sessions in order to resume and to seed. A download client
cannot work confined to the package container's storage.

4. Native user interface and OS integration. The application renders its window
natively through Win32 using the Slint toolkit, and integrates with Windows
toast notifications and the taskbar. It also opens a loopback TCP socket on
127.0.0.1 to enforce single-instance behaviour and to hand command line
arguments and magnet links to an already-running instance.

5. Optional local web interface. The user may enable an authenticated HTTP
server, bound to 127.0.0.1 by default, to control the running client from a
browser. This requires a listening socket that is not available to a container
application.

6. Command line usage. A console executable is included and exposed through an
appExecutionAlias so that the client can be scripted and run on machines without
a display. This requires a full-trust process.

The application collects no personal data. It contains no advertising, no
telemetry, no analytics and no crash reporting, and it creates no account. It is
free and open source under the MIT License.

--- NOTES ----------------------------------------------------------------------

Microsoft's own suggested wording for this capability is simply "This is a
native Win32 app and thus cannot run in the UWP sandbox." The longer text above
answers the "as much detail as possible" prompt, but the short form is what the
capability actually turns on.

runFullTrust is added automatically by every EXE-to-MSIX conversion tool, and is
expected for packaged desktop applications. Approval is routine.
